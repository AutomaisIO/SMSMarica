O que deve ir para o hub FHIR — e o que não deve

Onze recursos que, projetados do Salux para o Automais.Fhir, tornam a planilha de indicadores consultável pelo hub. Todos dentro do padrão R4: nenhum campo inventado, nenhuma extensão criada onde já existe elemento padrão, nenhum código gravado em system oficial sem confirmação.

A régua

Três princípios que decidem o que entra — e que valem mais que qualquer lista:

  1. Se o padrão já tem elemento, usa-se o elemento. O caso emblemático é Encounter.statusHistory: quatro indicadores de tempo por aba que hoje parecem exigir campo novo cabem num array que o R4 define desde sempre. Extensão só quando o padrão realmente não cobre.
  2. Recurso sem origem é recurso vazio. fhir.medication_administration já existe no hub com zero linhas — não por bug, mas porque o Salux não registra a hora da administração. Criar AdverseEvent antes de o NSP notificar em sistema repetiria o mesmo erro.
  3. Gestão não é clínica. RH, custo, compras, manutenção e faturamento não viram recurso FHIR só porque estão na mesma planilha. Eles têm casa: o schema de negócio do SMSMarica e os sistemas próprios.
O que o hub já tem — a linha de base

252.858 pacientes · 1.306.687 encontros (jan/2021 → jun/2026) · 1.266.520 diagnósticos CID-10 · 4.863.580 observações · 2.869.431 documentos · 1.688.313 prescrições · 3.140 profissionais. Tudo com meta.source apontando para a base de origem, como manda a proveniência multi-PEP. O plano abaixo é acréscimo sobre isso — não recomeço.

F1 · esforço Pequeno · complexidade

Encounter já no hub

enriquecer o que já existe

O que entra: statusHistory[] — a linha do tempo do atendimento, com period por status: arrived (chegada/totem) → triaged (classificação de risco) → in-progress (atendimento médico) → finished (saída).
participant[].period.start — o instante em que o médico assumiu o paciente.
reasonCode — motivo do atendimento · serviceType — setor/especialidade · serviceProvider → Organization · location[] → Location.

Origem no Salux: BAA: DT_CHEGADA, DT_ATENDIMENTO, DT_SAIDA, CD_MOTIVO_ATENDIMENTO, CD_UNIDADE · TRIAGEM · ACOLHIMENTO

Terminologia: http://hl7.org/fhir/encounter-status (statusHistory) · …/v3-ActCode (class, já em uso) · …/v3-ParticipationType (ATND / PPRF)

F3 · esforço Pequeno · complexidade

Location a criar

unidade, quarto e leito

O que entra: Um Location por leito, com partOf apontando para o quarto e este para a unidade — a hierarquia que o padrão espera. physicalType = bd (bed) / ro (room) / wa (ward). operationalStatus carrega ocupado, vago, em higienização ou isolamento.

Origem no Salux: LEITO (548) · QUARTO (43) · UNIDADE_HOSPITALAR · FIA_LEITO (situação e higienização)

Terminologia: …/location-physical-type → bd / ro / wa · …/v2-0116 → O ocupado, U vago, H higienização, I isolado, K contaminado, C fechado

{
  "resourceType": "Location",
  "status": "active",
  "name": "Leito 302-A",
  "mode": "instance",
  "physicalType": { "coding": [{ "system": "http://terminology.hl7.org/CodeSystem/location-physical-type",
                                 "code": "bd", "display": "Bed" }] },
  "operationalStatus": { "system": "http://terminology.hl7.org/CodeSystem/v2-0116",
                         "code": "O", "display": "Occupied" },
  "partOf": { "reference": "Location/quarto-302" },
  "managingOrganization": { "reference": "Organization/hmcml" }
}

Sem Location o hub nunca vai conseguir separar Adulto × Pediátrico × Materno Infantil — que é exatamente o recorte que a planilha exige e que hoje trava a entrega.

Destrava (estrutural): Habilita a taxa de ocupação (Adulto 11 · Pediátrico 8 · Materno 7) e o recorte por bloco — sempre junto com F2

O que entra: Um Organization por unidade, com o CNES como identifier — o mesmo identificador que o resto do ecossistema SMS Maricá já usa para unidade. Vira o serviceProvider de todo Encounter.

Procedure a criar

O que entra: status · code (SIGTAP) · subject · encounter · performed[x] · performer[].actor + performer[].function — é o function que responde 'parto assistido por enfermeiro obstétrico'.

O que entra: subject (único obrigatório) · event · date · seriousness · suspectEntity. É o recurso correto do R4 para evento de segurança do paciente — não forçar Condition nem Observation.

Measure + MeasureReport opcional

a própria planilha, como recurso FHIR

O que entra: O R4 tem um módulo de Quality Reporting feito exatamente para isto: Measure descreve o indicador (numerador, denominador, meta) e MeasureReport carrega o resultado de um período. A planilha de 94 linhas vira um catálogo versionado, e o resultado trimestral vira dado consultável.

Origem no Salux: Os próprios indicadores, uma vez calculados.

Uma restrição de arquitetura que não muda

O hub roda na DigitalOcean e não alcança o Oracle do Salux (rede interna 10.50.0.18). Toda projeção continua sendo feita pelo importador on-prem, que lê o Oracle e empurra para a API do hub. Nada aqui pede túnel novo nem acesso da nuvem ao hospital.

Conformidade que já está valendo e continua: identifier estável por recurso (salux-hcml:<hospital>-<ano>-<nr>), meta.source por base de origem, If-Match/ETag na atualização e idempotência por identifier — para reimportar sem duplicar.

O que não deve ir para o FHIR

Não por limitação técnica — por adequação. Empurrar esses dados para dentro do padrão distorceria o hub e não entregaria indicador melhor.

Grupo de indicadoresPor quê
Absenteísmo, vacância, rotatividade, acidentes, treinamentoSão dados de recursos humanos. O FHIR tem PractitionerRole, mas ele descreve vínculo assistencial — não folha, ponto nem afastamento. Forçar seria violar o padrão.
Custo médio de atendimento e de diáriaCusto hospitalar não é recurso FHIR clínico. Existe ChargeItem/Invoice no R4, mas modelam cobrança de item assistencial, não rateio de centro de custo. Fica na contabilidade.
Compras com pesquisa de preço e tempo de equipamento paradoSuprimentos e manutenção predial estão fora do escopo do FHIR. Device existe, mas para dispositivo clínico ligado ao paciente — não para gestão de parque de equipamentos.
Faturamento SUS (BPA / AIH) e alimentação do SIHO R4 tem Claim/ClaimResponse, mas modelados para seguro-saúde. O faturamento SUS brasileiro tem regra própria e já vive bem no Salux e no schema de negócio. Não vale a distorção.
Resolubilidade de ouvidoriasManifestação de ouvidoria não é registro clínico. Cabe no módulo de tickets do SMSMarica, que já existe, e não no hub.
Vigilância da CCIH (ITU/CVD, infecção de sítio cirúrgico)O evento até caberia em Condition ou AdverseEvent, mas o indicador exige denominador de dispositivo-dia e busca ativa pós-alta — processo de vigilância que não existe hoje. Projetar o recurso sem o processo só criaria um recurso vazio, como aconteceu com MedicationAdministration.
Recursos e elementos conferidos contra o FHIR R4 (4.0.1). Códigos de terminologia marcados como "confirmar" não devem ser gravados antes de verificação na fonte oficial. Linha de base lida do hub de produção em 23/07/2026. Gerado em 23/07/2026.
