### Veredito: **SUSTENTADO**

Tentei refutar e não consegui; o que encontrei aponta na direção da afirmação, com QUATRO condições que o projeto tem de assumir explicitamente.

1) Doc oficial MikroTik (página "Bridge", seção Bridge Firewall/NAT): "redirect - redirect the packet to the bridge itself (only valid in dstnat chain)"; "dst-nat - change destination MAC address of a packet (only valid in dstnat chain)"; "arp-reply - send a reply to an ARP request ... with the specified MAC address (only valid in dstnat chain)". E o "Packet Flow in RouterOS" coloca a ordem: Bridge NAT dstnat → Bridge Decision → Bridge Filter forward → Bridge NAT srcnat, com "A packet where the destination MAC address matches the bridge MAC address will be passed to the bridge input chain" (→ pilha IP). Ou seja: o redirect reescreve o dst-MAC ANTES da decisão de bridging, e a decisão então entrega o frame à CPU. A doc NÃO diz literalmente "e depois é roteado", só "to the bridge itself" — essa é a lacuna formal.

2) Mecanismo no kernel (RouterOS 7 = Linux 5.6.3, confirmado em Software Specifications/fórum). Li o fonte v5.6:
- net/bridge/netfilter/ebt_redirect.c: em NF_BR_PRE_ROUTING faz `ether_addr_copy(eth_hdr(skb)->h_dest, br_port_get_rcu(xt_in(par))->br->dev->dev_addr)` e `skb->pkt_type = PACKET_HOST` (ambos os hooks). 
- net/bridge/br_input.c: `br_handle_frame` só marca PACKET_HOST se dest == MAC da bridge ANTES do hook, mas a decisão real é em `br_handle_frame_finish` (chamado DEPOIS do NF_BR_PRE_ROUTING): `dst = br_fdb_find_rcu(br, eth_hdr(skb)->h_dest, vid); if (test_bit(BR_FDB_LOCAL, &dst->flags)) return br_pass_frame_up(skb);` → usa o h_dest JÁ reescrito → entrega local → ip_rcv. 
- net/ipv4/ip_input.c: `if (skb->pkt_type == PACKET_OTHERHOST) goto drop;` — por isso o fixup de pkt_type é o ponto crítico. Como redirect já seta PACKET_HOST, ip_rcv aceita; dst IP não é local → ip_forward → FIB → wg-dc, com NAT em postrouting. Nada no caminho exige que o dst IP seja do próprio roteador.
- net/bridge/netfilter/ebt_dnat.c (v5.6): dst-nat em PRE_ROUTING faz `if (ether_addr_equal(info->mac, dev->dev_addr)) skb->pkt_type = PACKET_HOST; else PACKET_OTHERHOST;` — ou seja, a variante `dst-nat to-dst-mac-address=<MAC da bridge>` também funciona em 5.6, mas só porque o patch de 2017 (Linus Lüssing, "bridge: ebtables: fix reception of frames DNAT-ed to bridge device": "the IP code drops it because the dnat target did not update the skb->pkt_type") entrou antes. Em kernels antigos (ROS 6) o dst-nat para o MAC da bridge era engolido em silêncio.

3) Fórum MikroTik — dois relatos coerentes, nenhum contrário ao mecanismo:
- "Redirecting packet from Bridge" (2011, ROS 5.6): Chupaka: `/interface bridge nat add chain=dstnat mac-protocol=ip dst-address=192.168.103.0/24 action=redirect` — "this will catch all packets ... redirect them to router's MAC address, then router will route packets according to its routing table"; o autor (ipl) respondeu "Excellent, That Works." → prova de ROTEAMENTO após redirect (kernel antigo, mas mesmo mecanismo).
- "Transparent bridge, mangle and prerouting" (fev/mar 2024, ROS 7, hEX): rplant recomenda exatamente o padrão do Motor B — `/interface bridge nat add action=redirect chain=dstnat dst-address=10.10.10.1/32 mac-protocol=ip in-interface=!ether1` para "kick incoming ... into router" e mandar por WireGuard, com a ressalva de DESABILITAR hw-offload na porta e assumir custo de CPU. O OP não voltou para confirmar → em ROS 7/hEX é recomendação de usuário experiente, não confirmação de campo.
- Contra-evidências examinadas e descartadas: "Bridge that catches some ports to itself" (2011): redirect contava mas "sem resposta" — o caso era o MK sem IP público/rota de retorno para a origem (problema de retorno IP, não do redirect). "Bridge dst-nat packets disappear" (ROS 7.11, CRS326): dst-nat para MAC de OUTRO host somem — cenário DSR num switch Marvell com offload; reforça duas cautelas: (i) preferir redirect a dst-nat; (ii) bridge NAT só vê frames processados pela CPU.

4) Condições sem as quais a afirmação FALHA na prática:
(a) hEX/MT7621: doc oficial "Layer2 misconfiguration": "when using bridge filter rules you need to enable forward all packets to the CPU, which requires the hardware offloading to be disabled". Com hw=yes em ether1 e ether4 o frame cliente→MAC do HPE é comutado em silício e a regra nunca casa (contador zero, sem erro). Portanto no hEX: `/interface bridge port set [find interface~"ether(1|4)"] hw=no` PERMANENTE (não mude hw em tempo de failover — a mudança derruba a bridge por instantes). No CCR (tile) não há switch chip → não se aplica (N7 confirma sem H).
(b) Usar `action=redirect`, não `dst-nat to-dst-mac-address`: o redirect não depende do MAC da bridge, que no CCR é auto-mac (herda combo1 — muda se a porta for removida/desabilitada, ccr.md §bridge). Se insistir em dst-nat, antes fixe `auto-mac=no admin-mac=48:8F:5A:8E:45:E4`.
(c) Fast-forward/fast-path caem quando há regras de bridge firewall (ccr.md mostra fast-forward=yes hoje); custo no CCR é irrelevante a 20 Mbps/9 núcleos; no hEX (CPU 880 MHz) a bridge em CPU sem fast-forward é o regime NORMAL a partir de (a) — medir throughput em bancada (esperado centenas de Mbps, suficiente).
(d) O matcher `dst-address` "only if MAC protocol is set to IPv4" — sob `mac-protocol=vlan` (variante tagged) não está documentado; fica a "captura cega" (N8d), como já previsto.

### Veredito: **SUSTENTADO**

NÃO CONSEGUI REFUTAR. A afirmação é o comportamento documentado e o uso clássico do bridge NAT; o que sobra são três condições de contorno que o projeto precisa fixar (hw-offload no hEX, regras desabilitadas × fast-forward, negação de matcher) e uma prova em hardware real por causa de um bug histórico em TILE.

1) Ordem oficial do fluxo (help.mikrotik.com, Packet Flow in RouterOS, seção Bridging): tanto no "Bridge Input" quanto no "Bridge Forward" o passo 1 é "A packet goes through the bridge NAT dst-nat chain, where MAC destination and priority can be changed", e só DEPOIS vem "Run packet through the bridge host table to make a forwarding decision. A packet where the destination MAC address matches the bridge MAC address will be passed to the bridge input chain." Portanto reescrever o dst-MAC para o MAC da bridge ANTES da decisão transforma um frame que seria encaminhado ao HPE em frame de entrada local; do bridge input ele segue para IP prerouting → routing decision → forward → postrouting como qualquer pacote roteado (conntrack, NAT, mangle/MSS aplicam-se normalmente). Não é necessário use-ip-firewall (isso só interessa para tráfego que CONTINUA bridgeado).

2) Definição oficial das ações (help.mikrotik.com, página Bridge, tabela Bridge NAT): action=redirect = "redirect the packet to the bridge itself (only valid in dstnat chain)"; action=dst-nat = "change destination MAC address of a packet (only valid in dstnat chain)" com to-dst-mac-address; matchers disponíveis: mac-protocol, dst-address ("Destination IP address", com mac-protocol=ip), dst-mac-address, in-interface, in-bridge. Ou seja, "frames IP unicast ao MAC do HPE com destino internet" é exatamente o que os matchers expressam (dst-mac-address=<MAC HPE> mac-protocol=ip in-interface=<porta do switch core> dst-address=!<redes internas>).

3) Semântica de protocolo (man ebtables, base do bridge NAT do RouterOS): "The redirect target will change the MAC target address to that of the bridge device the frame arrived on... in the PREROUTING chain, the MAC address of the bridge is used." É a receita canônica de interceptação transparente em bridge Linux: redirect em nat/PREROUTING + roteamento normal. Nada no IP stack exige que o dst-IP seja local para rotear — é a definição de roteador. Retorno: a resposta sai pela bridge com src-MAC = MAC da bridge para o MAC do cliente; hosts não validam src-MAC contra o cache ARP, então o cliente aceita, e o próximo pacote dele volta a ir ao MAC do HPE e é capturado de novo. Não há ICMP redirect (out-interface wg-dc ≠ in-interface bridge). O que NÃO é capturado (dst-address interno PMM) segue em ponte ao HPE com IP e MAC originais — compatível com N7/F3-4c.

4) Relatos de campo com a receita exata (fórum MikroTik): (a) "Redirecting packet from Bridge" — Chupaka: `/interface bridge nat add chain=dstnat mac-protocol=ip dst-address=192.168.103.0/24 action=redirect` "redirect them to router's MAC address, then router will route packets according to its routing table"; OP (ROS 5.6): "Excellent, That Works." (b) "Wierd setup. Ressalva de Chupaka: não funciona para tráfego dentro de túnel PPPoE (irrelevante aqui, LAN untagged). Não encontrei NENHUM relato de fracasso do redirect L2 em v7 (busquei "bridge nat redirect not working" — os resultados são todos de /ip firewall nat).

5) O ponto que quase refuta — bug em TILE: changelog oficial 7.2 (download.mikrotik.com/routeros/7.2/CHANGELOG, 2022-Mar-31; entrada datada de 7.2rc2, 2022-Jan-28): "*) bridge - fixed bridge filter and NAT rules on ARM64 and TILE devices;" — a thread "Bridge Filters Don't Seem to be working" (CCR2004/RB4011, 7.0b4–7.2rc1) mostra contadores zerados independentemente de hw-offload/fast-path até essa correção. Isso NÃO refuta, mas prova que bugs específicos de arquitetura existem nesse subsistema → a bancada tem de ser no hardware real (tile E mmips), não em CHR.

6) Fast path: Packet Flow oficial — o handler de fast path de bridge só é usado se "there are no bridge Calea, filter, NAT rules; use-ip-firewall is disabled; ... sniffer, torch, and traffic generator are not running; ... bridge dhcp-snooping is disabled". Logo, com regras de bridge NAT presentes o frame vai pelo caminho lento onde a NAT é aplicada (coerente com V3). NÃO documentado: se regra DESABILITADA conta como "rule" para desligar fast-forward/fast-path — isso decide o "custo zero em normal" no hEX e tem de ser medido (o CCR já não usa hw-offload: ccr.md:81-82, portas hw=yes sem flag H; mas usa fast-forward: 02-l2-l3.txt:217-222, 5,2 M pacotes).

7) CAVEAT FORTE PARA O hEX (MT7621), que limita a afirmação: hw-offload é ativo por padrão no hEX e frames offloaded nunca chegam à CPU — doc Bridge Hardware Offloading: "the packet will not be visible to RouterOS ... because the packet was already processed by the switch chip and never reached the CPU"; doc Layer2 misconfiguration: "when using bridge filter rules you need to enable forward all packets to the CPU, which requires the hardware offloading to be disabled"; EdPa (MikroTik, thread crs3xx): "Creating these rules will not disable HW-offloading, but they probably will not work correctly either as the frames are forwarded through the switch chip instead of the CPU." Ou seja: no hEX a afirmação só é verdadeira com hw=no nas portas da bridge (ether1 e ether4 no mínimo) — CPU bridging PERMANENTE (RB750Gr3 aguenta com folga os ~20-100 Mbps de uma unidade), ou alternância de hw= na entrada da contingência (a doc avisa que mudar propriedades de offload "can trigger a switch chip reset, temporarily disabling all Ethernet ports"). Isso derruba, como está, o item 10 do projeto ("no hEX bridging por CPU só durante a contingência") — precisa virar decisão explícita: hw=no fixo nos hEX ou toggle testado. A observação do template (failover-hex.rsc:10-12, "nenhum hEX precisou de hw=no") mede rx-packet da ether, não visibilidade pela CPU, e não serve de prova.

8) Detalhes ainda não provados (menores): negação `dst-address=!10.0.0.0/8` no bridge nat (alternativa segura: regra `action=accept` para destinos internos ANTES da regra de captura — accept encerra a chain dstnat); e a equivalência prática entre `redirect` e `dst-nat to-dst-mac-address=<MAC da bridge>` (por ebtables, redirect em PREROUTING usa o MAC da bridge — devem ser equivalentes; testar os dois).

## C5. O DC 10.135.16.119 faz recursão para a internet e responde a `:resolve p<rnd>.dnsprobe.automais.io` (zona wildcard própria), de modo que a sonda prova 'DC vivo E internet da PMM' sem depender de TCP/UDP do .254 atravessar a borda

RESUMO: a premissa factual (DC recursivo + responde ao .254) é PROVÁVEL mas NUNCA FOI MEDIDA; e a conclusão ("prova internet da PMM") é MAIS FORTE do que a sonda entrega. Não consegui refutar, mas também não dá para sustentar sem 4 correções de desenho.

1) O que o material sustenta a favor. Em 08-conexoes-todas.txt há 105 conexões udp/53 de 28 hosts (celulares Apple/Android, PCs) para 10.135.16.119/.17/.18 — os clientes usam os DCs como ÚNICO resolvedor e navegam na internet (cache de 1.477 nomes públicos: Apple, TikTok, Kwai, Microsoft). Não há vestígio de proxy explícito: zero WPAD, zero conexões a :3128/:8080, DHCP option 252 desconhecida (hosts.md:335; critico.md:23). Logo, em regime normal, nomes públicos são resolvidos VIA DC → o DC (ou seu forwarder) faz recursão para a internet. Isso é inferência, não medição: o retrato foi tirado em failover com :53 redirecionado para 8.8.8.8/9.9.9.9 (flag d), então não existe UMA resposta do DC a nome público no material. Também não há registro de nenhuma consulta do .254 ao DC (o /ip dns do MK usa 8.8.8.8 + 192.168.0.1 — 03-dhcp-dns.txt:507-509).

2) "Sem depender de TCP/UDP do .254 atravessar a borda" — correto e relevante: 10.135.16.119 é destino INTERNO (HPE → core PMM), não passa pela borda NAT/proxy que barrou TCP 443/UDP 53 do .254 no CAPS AD (SKILL.md:392). Isto é, o DC pode responder ao cliente com lease e devolver REFUSED/SERVFAIL ao .254. Só o teste decide.

3) O que a sonda NÃO prova, mesmo sendo verdadeira: ela prova "DC vivo ∧ caminho de recursão do DC até os autoritativos de automais.io". Não prova que TCP dos CLIENTES atravessa a borda/proxy. Os forwarders do DC podem sair por caminho/política diferente da navegação dos clientes (DNS liberado direto no firewall; DC em outra rede/link). Portanto o caso "TCP morto, ICMP vivo" (V7) NÃO é coberto pela sonda DNS-via-DC nem quando a afirmação é verdadeira — a frase "SE FALSA: resta só ICMP" está mal enquadrada: a sonda de identidade de lease com TCP (M3-b) é necessária de qualquer modo para fechar R3, ou pelo menos como verificação periódica. 4) Falsos positivos concretos a neutralizar:
 a) Sinkhole local: se o forwarder do DC for um filtro (FortiGate/Umbrella on-prem/pfBlocker) que, ao perder a internet/rating, responde um IP de bloqueio sintetizado LOCALMENTE, o DC devolve um A e o MK conclui "internet OK". Correção obrigatória: comparar o IP retornado com a constante da zona wildcard (`:resolve` devolve o IP; ou netwatch dns com validação), nunca aceitar "qualquer resposta".
 b) RFC 8198 (aggressive NSEC): se automais.io/dnsprobe for assinado com NSEC e o forwarder do DC for validador (Unbound tem aggressive-nsec habilitado por padrão nas versões recentes), a RFC permite SINTETIZAR resposta positiva de wildcard a partir do cache — p<rnd> seria respondido sem ir à internet. Correção: manter dnsprobe.automais.io SEM DNSSEC (ou NSEC3 opt-out) e TTL curto.
 c) Cache no DC: nome fixo (netwatch host=) seria respondido do cache do DC pelo TTL após a internet cair → o rótulo aleatório é obrigatório, o que impõe script (`:resolve ... server=10.135.16.119`), não netwatch type=dns (host fixo).

5) Falsos negativos / temporização: com forwarders padrão, o Windows DNS só devolve SERVFAIL após ~11,5 s (ForwardingTimeout 3 s, RecursionTimeout 8 s, +overhead — doc MS KB2834250); o cliente DNS do RouterOS desiste em query-total-timeout=10 s (03-dhcp-dns.txt:518). Consequência: cada sonda que falha custa ~10 s de bloqueio de script — a sonda DNS tem de rodar em job próprio (scheduler separado, resultado em address-list com timeout), não dentro do tick que também faz os pings. E, em contingência, o MK precisa de rota /32 para 10.135.16.119 (e .17) via 10.3.74.1 pref-src 10.3.74.254; sem ela a consulta segue a default pelo wg-dc, falha para sempre e o retorno automático nunca acontece. Se o DC recorrer a um resolvedor da PMM que morre com a internet OK, a sonda falha sozinha — coberto pelo OR com ICMP.

6) Viabilidade RouterOS 7.23 confirmada: `:resolve <domain-name> [server@vrf] [server-port] [type]`; "results won't be cached when server is specified"; em falha lança erro (capturar com :do on-error). Netwatch type=dns tem dns-server=, record-type, timeout (default 3 s — curto para resolução fria via DC; subir para ≥5 s) e src-address.

CONCLUSÃO: manter a sonda DNS-via-DC como sinal de "AD vivo + recursão do DC", com validação do IP esperado, rótulo aleatório, rota pinada e job próprio; NÃO a tratar como prova de internet dos clientes. O detector precisa de uma terceira perna TCP pelo caminho do cliente (M3-b) ou, no mínimo, de teste de campo que mostre que na topologia da PMM "DC resolve" ⇔ "cliente navega".

## C6. `/ip dhcp-server alert` emite DISCOVER 1×/min (doc), a OFFER do servidor real chega via relay com src-MAC do HPE e popula `unknown-server`; `alert-timeout=3m` esvazia após 3 min sem OFFER

PARTE 1 (DISCOVER 1×/min) — SUSTENTADA pela doc oficial, verbatim: "The detector operates as a DHCP client itself, sending discovery requests once per minute to catch unicast replies that might otherwise go undetected." (help.mikrotik.com DHCP → Alerts; texto histórico do wiki: "The rogue DHCP detector acts as a DHCP client as well and sends out DHCP discover requests once a minute"). Fórum (thread 152003) confirma na prática: "DHCP alert works by sending a probe for other DHCP servers".

PARTE 2 (OFFER relayada popula unknown-server com o MAC do HPE) — PLAUSÍVEL, não documentada. `unknown-server` é "List of MAC addresses of detected unknown DHCP servers" (string, separada por vírgula — ex. real: `unknown-server=E0:CB:4E:0C:4A:06`). Como é lista de MACs L2 e a OFFER do 10.1.201.254 chega à VLAN 10.3.74.0/24 injetada pelo relay (RFC 2131 §4.1 / RFC 1542: relay entrega ao cliente pela interface do giaddr, unicast a chaddr/yiaddr ou broadcast se flag), o único src-MAC visível é o do relay — o HPE 94:3F:C2:DF:49:D3 (P7). Ressalvas: (a) o MAC gravado pode ser o "MAC de sistema" do stack HPE e não o da SVI que responde ARP — não presumir, LER na bancada; (b) se a PMM tiver allow-list de MAC no DHCP (V7 sugere políticas por lease), o MK NUNCA recebe OFFER com DHCP vivo → retaguarda ligaria em regime normal para sempre; (c) `unknown-server` é string com vários MACs — o script tem de usar `:find` (substring), não igualdade.

PARTE 3 ("alert-timeout=3m esvazia após 3 min SEM OFFER") — NÃO SUSTENTADA e provavelmente FALSA como redigida. Doc: "alert-timeout — Time after which the alert will be forgotten. If after that time the same server is detected, a new alert will be generated"; "unknown-server — The server is removed from this list after alert-timeout". Nada diz que detecções repetidas RENOVAM o timer. ### Veredito: **INCERTO**

RESUMO DO CÉTICO: a aritmética e o mecanismo estão CORRETOS, mas a afirmação, do jeito que está escrita, esconde quatro furos que só a bancada fecha — dois deles com evidência documental de que "funciona" não é o mesmo que "fail-safe". Não consegui refutar a parte técnica central; consegui refutar as CONSEQUÊNCIAS implícitas ("reflete o estado do túnel" ⇒ "a contingência está protegida") e mostrar que "sem buraco negro" só foi provado em UM sentido.

1) MTU/PMTU — a conta fecha COM MARGEM ZERO, e só no sentido de saída.
- Overhead WireGuard IPv4 = 20 (IP) + 8 (UDP) + 4 (header type) + 4 (key_idx) + 8 (counter) + 16 (Poly1305 tag) = 60 bytes. Fonte: struct message_data em messages.h (header + __le32 key_idx + __le64 counter + encrypted_data) e noise_encrypted_len = plain + NOISE_AUTHTAG_LEN. Logo 1420 + 60 = 1480 = PMTU medida. Exatamente o limite, zero de folga.
- O padding NÃO estoura: calculate_skb_padding() em send.c alinha a 16 (MESSAGE_PADDING_MULTIPLE = 16) mas faz min(mtu, ALIGN(...)) — um pacote interno de 1420 sai com 1420, não 1424. Ponto a favor da afirmação.
- O WireGuard Linux envia o pacote EXTERNO com DF=0 (socket.c send4(): `skb->ignore_df = 1; udp_tunnel_xmit_skb(..., df=0, ...)`). Consequência dupla: (a) se a PMTU real for menor que 1480 num dia ruim, o pacote externo NÃO some por DF — é fragmentado pelo dispositivo que impõe 1480 (se ele fragmentar em vez de descartar); (b) fragmentos UDP atravessando CGNAT são justamente o que CGNAT trata pior (fragmento não-inicial não tem porta) — ou seja, a "salvação" (a) vira um segundo buraco negro (b). RouterOS usa o módulo Linux mas NÃO documenta o DF do outer — é item de bancada (sniffer na ether3).
- `/ping size=` no RouterOS conta o pacote IP INTEIRO (fórum "PING from RouterOS - relationship with MTU": "RouterOS takes into account the IP and ICMP framing and sends a packet which totals X bytes"; F1 C15 confirma no ROS 7). Então "1480 passa, 1484 some" = PMTU total 1480: a leitura de P6 está correta. Mas foi medida (i) para um destino qualquer da internet, não para 177.136.233.75, e (ii) só de SAÍDA. A PMTU de ENTRADA (DC → CGNAT → CPE → CCR) pode ser diferente e NÃO pode ser medida com DF de fora (o CPE é CGNAT). O único jeito de medir é através do próprio túnel: ping DF de 1420 bytes internos vindo do DC.
- Furo estrutural do "PMTU por unidade" (N6): o MTU da interface WireGuard do DC (CCR2116) é ÚNICO para os 15 peers. O sentido DC→unidade é governado pelo MTU do DC, não pelo da unidade. Se UMA unidade tiver Connect com PMTU 1472 (PPPoE 1492 − 20) ou menor, o MTU 1420 do hub gera outer 1480 para ela e o buraco negro reaparece no download — por mais que a unidade tenha medido e clampado. O padrão tem de fixar MTU do hub = min(PMTU de todas as unidades) − 60 e MSS = MTU − 40 em TODAS, ou usar uma interface WG por classe de PMTU no DC.
- TCP fica protegido pelos clamps in/out (SYN nos dois sentidos → ninguém envia segmento > 1380; isso é independente do MTU do DC). O que NÃO fica: UDP com DF (QUIC/HTTP3 — Chrome envia DF; o navegador cai para TCP por conta própria, sem travar), DNS grande, fragmentos. ### Veredito: **INCERTO**

A afirmação é um pacote de três coisas com graus de prova muito diferentes. Resumo do julgamento: (A) a aritmética de MTU se sustenta com fonte primária; (B) "check-gateway=ping reflete o estado do túnel" é REFUTADA como suficiente — por raciocínio de protocolo e pela própria doc, ela é cega exatamente ao modo de falha que a afirmação diz eliminar (buraco negro de PMTU) e só funciona se o gateway for o IP do peer; (C) "o DC roteia/NATeia 10.203.0.0/24" não tem nenhum artefato observável no repo/snapshot (grep por 10.203, wg-dc, CCR2116, Eveo no repo: zero ocorrências; a segunda sessão ainda está criando) e carrega um risco concreto de negócio (egress de datacenter recusado por SISREG/DATASUS). Logo: incerto, com partes sustentadas e partes refutadas.

=== (A) MTU 1420 sobre PMTU 1480 — SUSTENTADO, mas com margem ZERO ===
1. Overhead WireGuard IPv4 = 20 (IP) + 8 (UDP) + 32 (cabeçalho data: type/reserved 4 + receiver index 4 + counter 8 + tag Poly1305 16) = 60 bytes → 1420 + 60 = 1480 = PMTU medido. Exatamente no limite, sem 1 byte de folga.
2. O padding do WireGuard NÃO estoura o MTU: `calculate_skb_padding()` no kernel (drivers/net/wireguard/send.c) faz `padded_size = min(PACKET_CB(skb)->mtu, ALIGN(last_unit, 16))` — pacote interno de 1420 recebe 0 bytes de padding; pacote de 1410 é alinhado a 1420 e não a 1424. Portanto o maior frame externo é 1480, nunca 1484.
3. O pacote EXTERNO do WireGuard sai com DF=0: em send4() (drivers/net/wireguard/socket.c) `skb->ignore_df = 1;` e `udp_tunnel_xmit_skb(..., df=false, ...)`. Consequência prática: se algum roteador no caminho da Connect fragmentar em vez de descartar, um externo >PMTU ainda passaria (fragmentado). Mas a medição de 02/09 mostrou descarte silencioso sem ICMP frag-needed — não se sabe se o elemento gargalo fragmenta quando DF=0; isso é medível em minutos (teste T1b).
4. MSS 1380 = 1420 − 40 está correto para IPv4/TCP sem opções e replica o padrão já em produção no CCR para wg-becape (`change-mss new-mss=1380 tcp-mss=1381-65535` in/out — 01-export.rsc:171-176). Doc Mangle: `new-mss=clamp-to-pmtu` alternativa (MTU da interface de saída − 40).
5. Evidência de campo A FAVOR (parcial): os três túneis WG existentes no CCR usam MTU 1420 sobre a MESMA Connect e estão com handshake recente (peer1 rx 1,6 MiB / tx 27,5 MiB; 04-firewall-vpn.txt:152-177). Evidência CONTRA a suficiência dessa prova: wg-becape transportou só keepalives (2 KiB/8 KiB) e automais-vpn é gestão (pacotes pequenos) — NINGUÉM ainda provou que frames externos de 1480 bytes fluem em volume nos DOIS sentidos por essa Connect. Handshake e ping pequenos passam por qualquer buraco negro de PMTU; é exatamente o sintoma "site abre e cai".
6. Lacuna não-TCP: o clamp de MSS só cobre TCP. UDP com DF (Linux/Android põem DF por padrão) acima de 1420 fará o MK gerar ICMP tipo 3/código 4 com origem 10.3.74.254 — que NÃO é o gateway que o cliente conhece (ele acha que fala com 10.3.74.1). Windows/Linux modernos aceitam PTB de qualquer origem desde que o cabeçalho citado bata com um fluxo existente, mas isso tem de ser demonstrado (teste T3b). QUIC (≤1350 no Chrome) não é afetado.

=== (B) check-gateway=ping "reflete o estado do túnel" — REFUTADO como suficiente; sustentado apenas como "reflete alcançabilidade do peer com pacote pequeno" ===
1. Pré-condição de forma: a doc IP Routing diz que não é possível usar check-gateway quando o gateway é uma interface não ponto-a-ponto "for obvious reasons, there is no known destination IP". Ou seja: `gateway=wg-dc` com check-gateway=ping não funciona; TEM de ser `gateway=10.203.0.1` (IP do peer). O tópico do fórum "Router OS 7.1, Wireguard, Check gateway with ping - Not working" (rota via WG virando unreachable ao ligar check-gateway=ping; segundo relato em 2023) nunca foi resolvido no tópico e é consistente com gateway=interface. O changelog 7.21 (2026-jan) traz "route - make check-gateway=ping work on p2p interface gateways" — o 7.23.2 já contém. Com gateway=IP, funciona; a afirmação usa <WGDC_PEER> (IP), então passa neste ponto.
2. Cegueira ao PMTU (o ponto que derruba a afirmação como escrita): a sonda do check-gateway é um ICMP echo pequeno (não configurável em tamanho), a cada 10 s, 2 falhas → unreachable (doc IP Routing; /routing/settings: check-gateway-ping-interval 10s [100ms..10m], check-gateway-ping-count 2, check-gateway-ping-timeout 1s [1ms..1s]). Um túnel cujo caminho externo passou a descartar 1480 e ainda passa 88 bytes continua "UP" para o check-gateway, enquanto todo TCP com payload cheio morre. É precisamente o buraco negro de PMTU descrito em P6. Portanto check-gateway=ping NÃO reflete "o estado do túnel" no sentido que importa (capacidade de transportar frames cheios); reflete só alcançabilidade do peer.
3. Cegueira ao DC: o ping é respondido pelo WireGuard do CCR2116 mesmo com a internet/NAT do DC quebrados. O item 4 do projeto ("3 sondas via wg-dc") cobre isso, mas então a afirmação de que o check-gateway "reflete o estado" precisa ser rebaixada a "é o gatilho de última instância", não o sensor.
4. Latência de detecção/retorno: 20–30 s com os timers default. O 7.23 permite ajustar em /routing/settings (global para TODAS as rotas com check-gateway, inclusive a do Starlink), mas o timeout máximo é 1 s: sobre CGNAT + CPE compartilhado com 39 terceiros e 126–147 syn-sent (N1), picos de RTT >1 s produzirão flaps falsos se o count for baixo. É preciso medir a distribuição de RTT MK→10.203.0.1 antes de apertar.
5. check-gateway=bfd não é alternativa: a doc BFD lista "enabling BFD for ip route gateways" como NÃO suportado — a configuração `/routing bfd configuration interfaces=all` existente no CCR (01-export.rsc:221-222) é inerte para rotas estáticas.
6. Tabela de roteamento: rotas recursivas só resolvem next-hop na tabela main (fórum 182235 + doc: "for a user-created table to be able to resolve the destination, the main routing table should be able to resolve the destination too"). Se o default via wg-dc for posto numa tabela própria (mangle para o tráfego capturado), use gateway direto = 10.203.0.1 (conectado via wg-dc), nunca uma canária recursiva fora da main.
7. Firewall local pode fazer o check-gateway mentir: a regra "HRD WireGuard VPNs" aceita só udp 51820,13299 em ether3 (01-export.rsc:161-162); wg-becape (51823) já está fora dela e só sobrevive porque o MK inicia a cada 25 s e o conntrack mantém o stream. Se wg-dc não tiver o listen-port aceito em ether3, tráfego vindo do DC após silêncio cai na "BLINDAGEM Connect eth3" e o túnel/check-gateway oscila. No DC, o input precisa aceitar ICMP echo de 10.203.0.0/24 na interface WG, senão o check-gateway nunca sobe.

=== (C) "o DC roteia/NATeia 10.203.0.0/24" — NÃO VERIFICÁVEL hoje + risco de egress ===
1. Nenhum artefato: repo e snapshot não têm nada sobre 10.203.0.0/24, wg-dc, CCR2116 ou Eveo. Só existe o precedente do relay via Becape (peer3 com allowed-address 0.0.0.0/0, default via 10.202.0.1 distance 3 — DESABILITADO, e as rotas /32 SISREG/SER via wg-becape também desabilitadas; ccr.md §3.2/§4.2). Ou seja, o desenho "default por túnel WG para um roteador Automais" já foi montado uma vez e está desligado — o projeto precisa dizer por quê, antes de repetir o padrão.
2. Checklist mínimo que o DC precisa exibir para a afirmação virar verdadeira: endereço 10.203.0.1/24 na interface WG; peer da unidade com allowed-address=10.203.0.10/32 (a doc WireGuard proíbe sobreposição de allowed-address entre peers na mesma interface); srcnat src-address=10.203.0.0/24 out-interface=<pública>; forward accept in-interface=wg-*; input accept icmp de 10.203.0.0/24; MSS clamp 1380 também no DC; MTU 1420 na interface WG do DC.
3. Risco de negócio (refuta "sustenta a unidade" mesmo com túnel perfeito): docs/sisreg-egress.md registra que o SISREG/DATASUS (189.28.130.13) RECUSA conexões vindas de IP de datacenter (DigitalOcean) e que a solução em produção foi sair por um IP brasileiro de operadora (Mundivox 201.76.184.254). O egress da contingência passa a ser 177.136.233.75 (Eveo, datacenter). Se SISREG/SER/gov.br rejeitarem, a unidade de REGULAÇÃO perde justamente os sistemas críticos durante a contingência. Precisa de teste explícito (T6); se falhar, o DC ou a unidade têm de manter /32 para esses destinos via wg-becape/Mundivox.

=== Conclusão ===
Sustentado: 1420+60=1480, padding limitado ao MTU, DF=0 no externo, MSS 1380. Refutado: "check-gateway=ping reflete o estado do túnel" como sensor único — precisa de gateway=IP e é cego a PMTU e ao DC; deve ser rebaixado a último gatilho e complementado por sonda DF de tamanho cheio (netwatch icmp com packet-size — a doc Netwatch diz que sondas ICMP são SEMPRE enviadas com DF — ou `/ping size=1420 do-not-fragment`). Incerto: DC (sem artefato) e egress SISREG/SER por IP de datacenter.
